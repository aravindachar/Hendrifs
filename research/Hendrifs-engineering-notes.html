The Hendrifs Android app for the Blackstar ID:Core V4, from USB basics to every bug we fixed (repo state at commit 34d0933 plus the uncommitted work of 17–19 Nov 2026)

You started with an app that talked to your amp using a guessed protocol. It produced wrong values, lag, snap-back, disconnects and a dead tuner. You ended with an app driven by a protocol you measured on the real amp, with tests built from real captured bytes. This page goes through it layer by layer, from the USB cable up to the knob under your finger. For each layer it covers what the thing is, how ours works, and which bug taught us that.

01The whole system in one picture

Each layer has one job and talks only to its neighbours. When something breaks, this map is how you work out which layer to look in.

In words: the amp and phone exchange 64-byte packets over USB. UsbHidTransport only moves bytes and knows nothing about what they mean. IdCoreProtocol is pure functions that turn bytes into meaning and back. AmpController owns the live state and the timing: what to send, when, and which incoming packets to ignore. MainActivity turns that state into small JSON updates for the WebView. index.html draws the amp and sends your taps back as JSON commands. Keeping the protocol pure and separate from I/O is what let us unit-test it with no amp attached.

02USB basics you now actually use

Point: a USB device is a bundle of interfaces, and each interface has endpoints, which are one-way pipes. Your amp shows up as several interfaces: audio in and out (so it can be a sound card) plus one HID interface for control. The app claims only the HID interface, so Android's audio stack keeps the sound-card side.

TermWhat it means here
VID / PID27D4 = Blackstar, 0013 = ID:Core V4. That's how the app recognises the amp when it's plugged in.
HID"Human Interface Device", the class used by keyboards and game pads. Vendors like it because the OS needs no special driver. Data moves in fixed-size reports, here 64 bytes.
Interrupt IN endpointThe amp → phone pipe. The host polls it, and we queue a read and wait up to 8 ms for it to finish (requestWait(8)).
Interrupt OUT / SET_REPORTTwo ways to send phone → amp. We try the OUT endpoint first and fall back to a HID control transfer.
OTG"On-The-Go" lets the phone act as the USB host. Android exposes this through UsbManager and needs a permission prompt.
override fun write(packet: ByteArray) {
    // Prefer the interrupt OUT endpoint; fall back to HID SET_REPORT.
    var n = epOut?.let { connection.bulkTransfer(it, packet, packet.size, 250) } ?: -1
    if (n < 0) n = connection.controlTransfer(0x21, 0x09, 0x0200, hid.id, packet, packet.size, 250)
    if (n != packet.size) throw IOException("USB write failed ($n/${packet.size})")
}

override fun read(): ByteArray? {
    if (!queued) { buffer.clear(); request.queue(buffer); queued = true }
    val done = try { connection.requestWait(8) } catch (_: TimeoutException) { return null }
        ?: throw IOException("USB connection lost")
    ...
}

controlTransfer(0x21, 0x09, 0x0200 …) is the standard HID request "SET_REPORT, output report, id 0", spelled out as raw numbers. Any HID device accepts it.

A short timeout instead of blocking forever means read() returns null after 8 ms of silence, so the worker loop can go back and send your next knob change. This is the fix for "reads starve writes" (bug 3).

Errors become exceptions. A null from requestWait means the cable is gone. The controller catches that one exception and starts reconnecting.

03Reverse engineering: how we learned the language

Point: the old code was copied from notes about the V1/V2 amps and never checked on a V4, and every symptom traced back to that. Reverse engineering is not magic. It's the scientific method applied to bytes: observe, form a hypothesis, test by sending, confirm by reading back.

Watch the ampprobe.py (Python + hidapi) sent the startup packet and printed every report while you turned each physical knob.
Watch the official appUSBPcap's driver wouldn't start, so we hooked Windows' WriteFile inside Architect with Frida and logged every packet it sent.
Change one thing at a timeOne knob or one button per step, so each new packet maps to exactly one control.
Form the ruleThe packets all fit one pattern: kind · first id · 00 · count · values.
Prove itWe sent our own packets from the PC, read the amp's state back, and listened to the result.

Here is the strip as text. Watching from the amp's side showed which byte each knob changes. Watching from Architect's side showed the commands only the PC sends, such as storing a patch, the tuner and patch names. Changing one variable per step is what made the captures readable. The rule we inferred was then tested by writing to the amp and reading it back.

The same rule covers everything. 03 02 00 01 5A is one knob. 03 01 00 2A …42 values is the whole sound, ids 1 to 42 in a row. 08 11 00 01 01 is kind 08 (amp-wide settings), id 0x11 (tuner), value 1, which means "tuner on". Once you know the rule, a new command is just a new id, and no new code path is needed.

The junk-bytes trap. The amp doesn't zero its buffer, so bytes after 4 + count hold whatever was there before. If you decode the whole 64 bytes, you read "values" that change at random. That alone produces "wrong values shown". The parser only reads up to the declared count, and patch names stop at the first NUL byte. A unit test (withJunk) fills the tail with garbage on purpose to prove this.

The two other surprises in the captures

  • The amp echoes everything. Every command you send comes straight back as if the amp's own knob had moved. Without handling this, the screen fights you (bug 2).
  • The amp repeats knob reports about every 10 ms while a knob moves. If you redraw on every one of them, the UI chokes.

What we decoded (the short version)

DirectionBytesMeaning
app → amp81 00 00 04 03 06 02 7AHandshake. The amp replies with version, live sound, globals and selected patch.
app → amp03 <id> 00 01 <v>Set one parameter. Delay time is the only 2-byte value: 03 1B 00 02 lo hi, 100–1000 ms.
app → amp02 01 <slot> 00Select patch 1–6.
app → amp02 02 slot len name then 02 03 slot 2B +43Store a patch: name packet, then 43 parameter bytes.
app → amp08 11 00 01 01 / 00Tuner on / off.
amp → app07 00 00 03 01 00 04Firmware 1.0.4.
amp → app02 06 slot 3C …Patch selected (the voice knob on the amp does this).
amp → app09 note cents+50 …Tuner reading, about 10 per second. Note 0 = no signal.

The full table is in research/V4-PROTOCOL.md. One rule from the hardware shaped the UI: each voice owns one patch slot (slot = voice + 1). That's why tapping a voice lamp selects a patch, and why "Store to amp" picks the slot for you.

04The protocol layer: pure functions you can test

enum class Control(val id: Int, val min: Int, val max: Int, val twoBytes: Boolean = false) {
    VOICE(0x01, 0, 5),
    GAIN(0x02, 0, 127),
    ...
    DELAY_TIME(0x1B, 100, 1000, twoBytes = true),
    GATE_AMOUNT(0x27, 0, 127);
}

fun setControl(c: Control, value: Int): ByteArray {
    val v = value.coerceIn(c.min, c.max)
    return if (c.twoBytes) pad(0x03, c.id, 0x00, 0x02, v and 0xFF, v shr 8)
    else pad(0x03, c.id, 0x00, 0x01, v)
}

fun parse(p: ByteArray): Event = when {
    b0 == 0x03 && b2 == 0 && n in 1..60 -> Event.Params(b1, block(p, n), whole = b1 == 1 && n >= 0x29)
    b0 == 0x08 ... -> Event.Globals(b1, block(p, n))
    b0 == 0x09 -> Event.TunerReading(note, name, cents = b2 - 50)
    ...
    else -> Event.Unknown(p)
}

The table is the protocol. Every id, range and the one 2-byte value sit in one enum. Fixing "wrong values" mostly meant correcting rows here.

coerceIn clamps at the edge, so a bug in the UI can never send 500 to a 0–127 knob.

Little-endian: 1000 ms = 0x03E8 is sent as E8 03, low byte first.

A sealed Event type means the rest of the app pattern-matches on meaning, never on raw bytes. Anything unrecognised becomes Unknown and is logged, not thrown.

Golden-byte tests. The 17 protocol tests use byte strings captured from the real amp and from Architect. One example is storeMatchesArchitectByteForByte: we read patch 1 from the amp, built the store packets, and asserted they equal what Architect sends, byte for byte. If someone "cleans up" the encoder later and breaks it, a test fails on the laptop, not on stage.

05The bugs, and what each one teaches

Each card gives the symptom you saw, the real cause, and the fix. The lesson line is the part to keep for other projects.

1 · Loading a preset made the amp go silent

SymptomTap a song preset and the amp goes quiet.
CauseWe loaded presets by sending the whole sound block (03 01 00 2B + 43 bytes). Byte 3 of that block is volume, and our presets had it as 0. The amp obeyed: volume zero. Separately, the store path wrote volume 0 into saved patches, which made them silent too.
Fixapply() now sends each control on its own (03 id 00 01 v), voice first, and never sends volume. Storing keeps the patch's real volume, falling back to the live one, then a safe default (0x41).
Lesson: in a binary protocol every byte you send is a command. There is no "unset". If you don't own a field's value, don't write that field. Writing the whole block was convenient and wrong.

2 · Knobs snapped back while you dragged

SymptomDrag gain from 40 to 90 and it flickers back to 50-something, then jumps.
CauseThe amp echoes every command. By the time the echo of "gain = 52" arrives, your finger is already at 70. The app trusted the echo and moved the knob back.
FixAn echo guard: when you change a control, the app records localUntil[id] = now + 500 ms. Single-knob reports for that id inside the window are ignored. Full-sound reports (a patch change) still win, and they clear all guards.
Lesson: when two sources can write the same value (your finger and the device), decide on purpose who wins and for how long. This is the same problem as optimistic UI in web apps.

3 · Lag and stutter

SymptomKnobs lag, the tuner stutters, and taps sometimes get lost.
CauseFour costs stacked up:
  • every packet copied a 3000-line log into state
  • every change pushed the whole state as JSON
  • the page rebuilt every button with innerHTML, even under your finger
  • the worker sent the whole outbox before reading, so reads starved
Fix
  • The log moved to a ring buffer that is read only when the console opens.
  • Coalescing: only the latest value per control is kept, sent at most every 25 ms.
  • The worker alternates one write with one read.
  • Kotlin pushes only changed fields.
  • JS redraws only "dirty" parts, once per animation frame.
Lesson: performance problems are usually work you didn't need to do, not slow code. Look for anything done per event (per packet, per frame) and ask: "does this need to happen at this rate, at this size?"
// set(): your finger. Store the newest value; overwrite older ones.
pendingControls[c] = v                          // a map, not a queue

// worker: one write, then one read, forever
while (running && gen == generation) {
    val out = outbox.poll() ?: nextControlPacket()
    if (out != null) { t.write(out); Thread.sleep(WRITE_GAP_MS) }
    val p = t.read()                             // ≤ 8 ms
    if (p != null) handle(p)
}

private fun nextControlPacket(): ByteArray? {
    for ((c, v) in pendingControls) {
        if (now - (lastSent[c] ?: 0) < CONTROL_GAP_MS) continue
        if (pendingControls.remove(c, v)) return setControl(c, v)
    }
    return null
}

Map instead of queue = coalescing. A drag produces 60 values a second. A queue would send all 60, late. A map keeps only the newest, so the amp always gets where your finger is.

remove(c, v) is atomic: it removes the entry only if it still holds v. If your finger moved in between, the newer value stays queued. That's a small lock-free concurrency trick.

Commands that must keep their order (patch select, store, handshake) go through a separate FIFO outbox. Knob values can be dropped; commands can't.

gen == generation means that after a reconnect, an old worker thread notices it's stale and exits instead of writing to a dead cable.

4 · Disconnects that never recovered

SymptomA cable wiggle or a missed handshake left the app dead until restart.
CauseThere was no retry and no reconnect, and errors surfaced as raw exception toasts.
Fix
  • The handshake is resent up to 4 times, 1.2 s apart, then one plain-language message.
  • On link loss, the app reconnects with exponential backoff (1 s, 2 s, 4 s).
  • It reattaches on ACTION_USB_DEVICE_ATTACHED.
  • A crash handler and a runCatching around each UI command keep one bad input from killing the app.
Lesson: design for failure as a normal state. Every I/O link needs an answer to "what happens when this goes away?", and the user-facing message should say what to do.

5 · The tuner did nothing

SymptomThe tuner page stayed blank.
CauseThe tuner command and reading format were guessed. Once captured, they turned out to be 08 11 00 01 01 and 09 note cents+50. A first fix then let the phone's pitch detector permanently block the amp's readings.
FixThe real tuner command, plus a second source: YIN pitch detection on the amp's USB audio. The two are arbitrated by recency: whichever produced a note in the last 400 ms is shown.
Lesson: when you merge two sources, don't hard-code a priority. Pick the one that is currently alive. Also be honest about what's unverified: the amp's USB audio arrived as digital silence in our PC test, so the phone-side tuner isn't proven yet.

06Threads and state: who touches what

Point: three threads are involved, and the rules are simple. The USB worker owns the I/O. A lock guards the shared byte tables. The UI only ever reads immutable snapshots.

Worker thread (AmpController.loop)

Blocking USB calls live here and never on the UI thread, because Android kills apps that block the main thread. It parses packets, updates live[] / globals[] under synchronized(lock), then publishes a new AmpState.

UI thread (MainActivity + WebView)

It collects the StateFlow, diffs it against what was last sent, and calls evaluateJavascript("PT.onState(...)"). Taps come back through @JavascriptInterface on a binder thread, so the bridge hops to runOnUiThread before touching anything.

Why StateFlow: it always holds the latest value, and a slow collector simply skips stale intermediate states. That's the right behaviour for a UI, because you want the current amp, not a replay of every step. The tuner has its own flow, so ten readings a second don't cause ten full-state diffs.

07Kotlin ↔ WebView bridge

Point: the UI is a web page inside the app. HTML, CSS and SVG let us draw brushed-gold plates, rotary knobs and patch cables far faster than native views would. The cost is a hand-made message protocol between the two worlds.

// JS → Kotlin: one entry point, JSON commands
HendrifsNative.send(JSON.stringify({ a: "set", c: "GAIN", v: 90 }))

// Kotlin → JS: only what changed
fields.forEach { (k, v) ->
    val str = v.toString()
    if (sent[k] != str) { sent[k] = str; diff.put(k, v) }
}
if (diff.length() > 0) js("PT.onState($diff)")

// JS: merge, mark dirty, draw once per frame
onState(d) { Object.assign(S, d); Object.keys(d).forEach(k => dirty.add(k)); scheduleRender(); }

One verb, many actions (a: "set" | "patch" | "songLoad" | "tuner" …) keeps the native surface tiny and easy to audit.

Diffing by string is crude but correct: if the JSON text didn't change, the screen doesn't need to.

requestAnimationFrame batches any number of updates into one redraw per screen refresh. Buttons are built once and then only have classes toggled, so a tap is never lost to a rebuild.

Browser preview: with no native bridge, index.html#demo runs a tiny fake amp in JS. That's how we designed the voice lamps and the OnePlus Pad layouts on the PC.

08Pitch detection: how YIN finds the note

Point: a plucked string repeats its waveform every period T, and frequency = sample rate ÷ T. YIN finds T by asking: "if I shift the signal by τ samples, how different is it from itself?" At the true period, the difference drops close to zero.

// 1. difference function
for (tau in 1..maxLag) { d[tau] = Σ (x[i] - x[i + tau])² }
// 2. cumulative mean normalised difference
cmnd[tau] = d[tau] * tau / (d[1] + … + d[tau])
// 3. first tau under threshold, then slide to its local minimum
if (cmnd[tau] < 0.12) { while (cmnd[tau + 1] < cmnd[tau]) tau++; break }
// 4. parabolic interpolation → sub-sample precision
shift = (a - c) / (2 * (a + c - 2 * b))
return rate / (tau + shift)

// Hz → note + cents
midi  = 69 + 12 * log2(hz / 440)
cents = (midi - round(midi)) * 100

Normalising (step 2) stops the curve from trivially reaching zero at τ = 0, so a fixed threshold works for any loudness.

Lag range: rate/1400 to rate/60 covers about 60 Hz (drop tunings) up to high frets. The code decimates audio to 24 kHz first, which halves the work.

Interpolation matters: at 24 kHz a low E's period is about 292 samples. Being off by one sample is roughly 6 cents, too coarse for a tuner. Fitting a parabola through the three points around the dip recovers the in-between value.

A silence gate (RMS < 0.004) returns "no note" instead of guessing at noise.

09.bstar files: parsing someone else's format safely

Point: Architect saves patches as small XML documents (<Sound><Amplifier><Gain>…). We mapped each tag to a Control by loading a known patch (Mayer Gravity) through Architect and comparing the bytes it sent with the XML values.

val f = DocumentBuilderFactory.newInstance().apply {
    setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true)
    setFeature("…/disallow-doctype-decl", true)
    isExpandEntityReferences = false
}
val root = f.newDocumentBuilder().parse(input).documentElement
require(root.tagName == "Sound") { "Not an Architect patch" }
put(Control.GAIN, num(amp, "Gain"))     // clamps to min..max

Why disable DOCTYPE? XML can define "entities" that pull in local files or expand into gigabytes (XXE, the "billion laughs" attack). Imported files come from strangers, so the parser refuses those features outright.

Validate, then clamp. We check the root tag, and every number goes through the same min..max clamp as a knob.

Round-trip test: BstarFormatTest parses a fixture and writes it back.

10Build, tooling and the small things that bit

  • Gradle build output lives outside OneDrive (~/.gradle-builds/hendrifs). OneDrive syncing locks files mid-build and causes random failures.
  • Lint caught local.properties: Windows paths in a properties file need escaped backslashes (C\:\\Users…) and LF line endings.
  • A Kotlin comment bug: writing assets/community/*.bstar inside a KDoc opens a nested comment (/*) that never closes. The compiler error points far from the cause.
  • A fake transport (FakeAmpTransport) speaks the real V4 formats, including echoes, so demo mode behaves like the amp.
  • Release pipeline: ./gradlew testDebugUnitTest assembleRelease lintRelease, then copy the APK to Hendrifs.apk.

11Still open: what isn't proven yet

A good engineer keeps this list as carefully as the done list.

  • The latest build hasn't been run end to end on the OnePlus Pad with the amp. The phone reported patch switching failing earlier, and no USB log was captured.
  • The phone-side YIN tuner depends on the amp's USB audio, which was silent in the PC test. The cause is unknown (possibly the amp's USB audio routing).
  • CabRig and footswitch globals follow the confirmed 08 id 00 01 v pattern, but haven't been tested one by one.
  • The amp tuner's note numbering (1 = E …) came from a handful of readings, not a full chromatic sweep.

12What you can now say you know

  • USB device model: interfaces, endpoints, HID reports, VID/PID, OTG host mode on Android.
  • Protocol reverse engineering: differential captures, one-variable-at-a-time experiments, API hooking when packet capture fails, confirming by write-and-read-back.
  • Binary encoding: length-prefixed blocks, little-endian multi-byte values, NUL-terminated strings, ignoring undefined trailing bytes.
  • Real-time I/O design: coalescing (latest-value-wins), separate FIFO for ordered commands, read/write interleaving, short timeouts.
  • Two-writer conflicts: echo suppression with time windows, authoritative full-state resets.
  • Resilience: handshake retry, exponential backoff, generation counters for stale threads, failure-aware messages.
  • Concurrency on Android: worker thread versus main thread, locks around shared tables, StateFlow conflation, binder-thread hops.
  • Hybrid apps: a JSON message bridge, diff-only pushes, dirty-set rendering on requestAnimationFrame.
  • DSP: YIN pitch detection, normalisation, parabolic interpolation, Hz to MIDI to cents.
  • Safe parsing: XXE-hardened XML, validate-then-clamp.
  • Testing strategy: golden-byte tests from real captures, adversarial fixtures (junk tails), fakes that mimic real device quirks.
  • Debugging mindset: every symptom ("silent", "jumps", "lags") traced to one mechanism, not patched over.

How to keep growing from here: pick one layer and rebuild it from memory without looking. The protocol parser is the best start because its tests will tell you when you're right. Then read AmpController.loop and explain to yourself, out loud, why each line exists. If you can explain it, you own it.
